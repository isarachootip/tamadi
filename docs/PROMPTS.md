# Prompt สำหรับ Antigravity แบ่งตามระยะ

วิธีใช้
1. เปิดโฟลเดอร์ C:\atgv\tamadee เป็น workspace
2. วาง "บริบทร่วม" เป็นข้อความแรกของทุก session ใหม่ (หรือใส่เป็น rules ของ workspace)
3. รันทีละระยะ ตรวจผลตาม "เสร็จเมื่อ" ก่อนไประยะถัดไป
4. ค่าที่อยู่ใน [วงเล็บเหลี่ยม] ต้องแก้เป็นค่าจริงก่อนรัน

## บริบทร่วม (วางก่อนทุกระยะ)

```
คุณกำลังพัฒนา Tamadee ("ทำมาดี ทำมาขาย") ซึ่งเป็น marketplace หลายผู้ขายสำหรับตลาดไทย สินค้าไม่เกิน 500 รายการ

อ่านไฟล์เหล่านี้ก่อนเริ่มงานทุกครั้ง: README.md, PLAN.md, docs/PHASE0.md

โครงสร้าง
- apps/backend     : Mercur (บน Medusa v2), PostgreSQL, Redis -> bwebtamdi.tamadee.online
- apps/storefront  : Next.js + Tailwind + TypeScript โค้ดชุดเดียว ให้บริการ 2 โดเมน
                     tamdi.tamadee.online (layout มือถือ, PWA) และ webtamdi.tamadee.online (layout จอใหญ่)
- packages/ui      : design tokens, โลโก้, มาสคอต, component ที่ใช้ร่วมกัน
- infra/           : docker-compose, Caddyfile
- brand/           : ไฟล์ SVG โลโก้และมาสคอต "น้องทำมะดิ"

แบรนด์
- สี: #111111, #C6F432 (สีเน้น), #FFFFFF, #F1F1EE
- ฟอนต์: Space Grotesk (โลโก้และตัวเลข), Anuphan (ภาษาไทย)
- สไตล์: minimal, ตัวอักษรหนา, มุมโค้งมน, ปุ่มหลักอยู่ครึ่งล่างของจอ, ปุ่มกดสูงอย่างน้อย 44px, มี dark mode

กติกา
- ใช้ TypeScript ทั้งหมด ข้อความในหน้าจอเป็นภาษาไทย สกุลเงิน THB
- ก่อนติดตั้งหรือใช้ library ใด ให้เปิดเอกสารทางการของเวอร์ชันล่าสุดก่อน ห้ามเดาคำสั่งหรือ API จากความจำ
- ห้ามใส่รหัสผ่านหรือ key ลงในโค้ด ใช้ .env และอัปเดต .env.example ทุกครั้งที่เพิ่มตัวแปร
- ทำเฉพาะงานของระยะที่สั่ง ถ้าเจอสิ่งที่ต้องตัดสินใจนอกขอบเขต ให้หยุดแล้วถาม
- ห้ามรันคำสั่งที่ลบข้อมูลหรือแก้ระบบบน production โดยไม่ถามก่อน
- จบงานทุกครั้งให้: รัน build และ test ให้ผ่าน, commit พร้อมข้อความที่อธิบายงาน, แล้วสรุปว่าทำอะไร ทดสอบอะไร และอะไรยังไม่ได้ทำ
```

## ระยะ 0: เตรียม repo และระบบพื้นฐาน

```
เป้าหมาย: ทำให้ workspace นี้เป็น monorepo ที่พร้อมพัฒนา และรันบริการพื้นฐานบนเครื่องได้

งาน
1. git init (ถ้ายังไม่มี) และตั้ง monorepo ด้วย pnpm workspaces ตามโครงสร้างในบริบทร่วม
2. ตรวจ infra/docker-compose.yml และ infra/Caddyfile ซึ่งเป็นฉบับร่างที่ยังไม่เคยทดสอบ แก้ให้ถูกต้อง
3. เพิ่ม docker-compose.dev.yml สำหรับพัฒนาบนเครื่อง (Postgres, Redis เปิดพอร์ตเฉพาะ localhost)
4. สร้าง packages/ui พร้อม design tokens จากสีและฟอนต์ของแบรนด์ และคัดลอก SVG จาก brand/ เข้ามาเป็น component
5. เขียน docs/DEPLOY.md: ขั้นตอนตั้ง VPS [ระบบปฏิบัติการ/RAM ของ VPS] ตั้งแต่ติดตั้ง Docker ถึงรัน compose

เสร็จเมื่อ
- docker compose -f infra/docker-compose.dev.yml up -d รันได้ และเชื่อมต่อ Postgres กับ Redis ได้
- pnpm install ผ่านโดยไม่มี error
- อย่าเพิ่งติดตั้ง Mercur หรือสร้างหน้าร้านในระยะนี้
```

## ระยะ 1: Backend marketplace

```
เป้าหมาย: มี backend marketplace ที่รันบนเครื่องได้ พร้อมข้อมูลตัวอย่าง

งาน
1. เปิดเอกสารทางการของ Mercur (docs.mercurjs.com) และ Medusa v2 แล้วติดตั้ง Mercur เวอร์ชันล่าสุดลงใน apps/backend ตามวิธีที่เอกสารระบุ
2. ตั้งค่า: region ไทย, สกุลเงิน THB, ภาษี VAT 7%, ภาษาไทย
3. สร้างหมวดหมู่สินค้า: [รายชื่อหมวดหมู่]
4. ตั้งกติกา marketplace: ผู้ขายสมัครแล้วต้องรอผู้ดูแลอนุมัติ, ค่าคอมมิชชัน [X]%
5. เขียน seed script: ผู้ดูแล 1 คน, ผู้ขายตัวอย่าง 3 ราย, สินค้าตัวอย่าง 30 รายการพร้อมรูป placeholder
6. ตั้ง CORS ให้ tamdi.tamadee.online, webtamdi.tamadee.online และ localhost
7. เพิ่มบริการ backend และ worker ลงใน infra/docker-compose.yml
8. เขียน docs/BACKEND.md: วิธีรัน, URL ของ admin และ vendor panel, รายการ API ที่หน้าร้านจะใช้

เสร็จเมื่อ
- login เข้า admin ได้ เห็นผู้ขายและสินค้าตัวอย่าง
- ผู้ขายตัวอย่าง login เข้า vendor panel และเพิ่มสินค้าได้
- เรียก Store API ดึงรายการสินค้าได้จาก localhost
- รายงานว่าฟีเจอร์ใดของ Mercur อยู่ในรุ่น Enterprise และเราไม่ได้ใช้
```

## ระยะ 2: หน้าร้านมือถือ (tamdi.tamadee.online)

```
เป้าหมาย: หน้าร้านมือถือที่ลูกค้าเลือกสินค้าและใส่ตะกร้าได้ โดยดึงข้อมูลจริงจาก backend

อ้างอิงดีไซน์: [วางลิงก์หรือภาพหน้าจอจาก canvas: หน้าแรก, หน้าสินค้า, ตะกร้า, ผู้ช่วย AI]

งาน
1. สร้าง apps/storefront ด้วย Next.js (App Router) + Tailwind ใช้ tokens และ component จาก packages/ui
2. ทำหน้าจอ layout มือถือ (กว้าง 390px เป็นหลัก):
   - หน้าแรก: โลโก้, ช่องค้นหา, แบนเนอร์, แถบหมวดหมู่, สินค้าแนะนำ, เมนูล่าง 5 ปุ่ม
   - รายการสินค้าตามหมวดหมู่ และผลการค้นหาพร้อมตัวกรอง
   - หน้าสินค้า: รูปหลายรูป, ตัวเลือกสินค้า, ชื่อร้านผู้ขาย, ปุ่ม "ใส่ตะกร้า" และ "ซื้อเลย"
   - หน้าร้านของผู้ขาย
   - ตะกร้า: จัดกลุ่มสินค้าตามผู้ขาย
   - สมัครสมาชิก, เข้าสู่ระบบ, บัญชีของฉัน, รายการถูกใจ
3. ทำเป็น PWA: manifest, ไอคอนจาก brand/app-icon.svg, ติดตั้งลงหน้าจอหลักได้
4. รองรับ dark mode
5. หน้าผู้ช่วย AI ให้ทำเฉพาะโครงหน้าจอไว้ก่อน ยังไม่ต้องเชื่อม AI

เสร็จเมื่อ
- เปิดบนมือถือจริงหรือ emulator แล้วเดินจากหน้าแรก -> สินค้า -> ตะกร้า ได้ด้วยข้อมูลจาก backend
- Lighthouse หมวด Performance และ Accessibility บนมือถือ ได้ 90 ขึ้นไป (รายงานคะแนนจริง)
- ยังไม่ต้องทำขั้นตอนชำระเงิน
```

## ระยะ 3: ชำระเงิน จัดส่ง และจ่ายเงินผู้ขาย

```
เป้าหมาย: ลูกค้าสั่งซื้อและจ่ายเงินได้จริงในโหมดทดสอบ ออเดอร์แยกตามผู้ขาย

ข้อมูลที่ต้องมีก่อนเริ่ม: gateway ที่เลือก = [Opn Payments / 2C2P / อื่นๆ] และ test key อยู่ใน .env แล้ว

งาน
1. ตรวจก่อนว่ามี payment provider สำหรับ Medusa v2 ของ gateway นี้ที่ยังดูแลอยู่หรือไม่ ถ้าไม่มีให้เขียน provider เองตามเอกสาร Medusa แล้วรายงานว่าเลือกทางใดเพราะอะไร
2. รองรับ: พร้อมเพย์ QR (ยืนยันยอดอัตโนมัติด้วย webhook), บัตรเครดิต/เดบิต, เก็บเงินปลายทาง
3. หน้าชำระเงินหน้าเดียว: ที่อยู่, วิธีส่ง, วิธีจ่าย, โค้ดส่วนลด, สรุปยอด
4. ค่าจัดส่ง: [ผู้ขายส่งเอง คิดค่าส่งต่อร้าน / Tamadee รวมส่ง]
5. เมื่อจ่ายเงินสำเร็จ: แยกออเดอร์ตามผู้ขาย, แจ้งผู้ขาย, ส่งอีเมลยืนยันให้ลูกค้า
6. หน้าติดตามออเดอร์ของลูกค้า และการอัปเดตสถานะจัดส่งใน vendor panel
7. รายงานยอดที่ต้องโอนให้ผู้ขายแต่ละรายต่อรอบ (หักค่าคอมมิชชัน) ส่งออกเป็น CSV ยังไม่ต้องโอนอัตโนมัติ
8. เขียน test สำหรับ webhook: จ่ายสำเร็จ, จ่ายไม่สำเร็จ, webhook ซ้ำ, ลายเซ็นไม่ถูกต้อง

เสร็จเมื่อ
- สั่งซื้อสินค้าจาก 2 ร้านในตะกร้าเดียว จ่ายด้วยพร้อมเพย์โหมดทดสอบ แล้วได้ 2 ออเดอร์ย่อยที่สถานะถูกต้อง
- webhook ที่ลายเซ็นไม่ถูกต้องถูกปฏิเสธ
- ห้ามใช้ key จริง (live) ในระยะนี้
```

## ระยะ 4: หน้าร้านจอใหญ่ (webtamdi.tamadee.online)

```
เป้าหมาย: โค้ดชุดเดียวกันแสดง layout จอใหญ่เมื่อเข้าจาก webtamdi.tamadee.online

งาน
1. เลือก layout ตาม hostname ที่เข้ามา (middleware) โดยใช้ component และ logic เดิมจากระยะ 2-3
2. Layout จอใหญ่: เมนูบน, ตารางสินค้า 4-5 คอลัมน์, ตัวกรองด้านข้าง, หน้าสินค้า 2 คอลัมน์, ตะกร้าแบบแผงด้านขวา
3. SEO: metadata ต่อหน้า, sitemap, structured data ของสินค้า, canonical ชี้ไปที่ webtamdi เพื่อไม่ให้เนื้อหาซ้ำกับ tamdi
4. เพิ่มบริการ storefront ลงใน infra/docker-compose.yml และตรวจ Caddyfile ให้ 2 โดเมนชี้มาที่บริการนี้

เสร็จเมื่อ
- ทดสอบด้วยการตั้ง hosts file หรือ header แล้ว 2 โดเมนแสดง layout ต่างกันจาก build เดียว
- ขั้นตอนสั่งซื้อทำงานครบบนจอใหญ่
```

## ระยะ 5: ฟีเจอร์ล้ำ (ทำทีละข้อ แยก session)

```
เลือกทำ 1 ข้อต่อ session: [5.1 / 5.2 / 5.3 / 5.4]

5.1 ผู้ช่วย AI "น้องทำมะดิ"
- แชตภาษาไทย รับคำขอ เช่น "หาชุดไปทะเล งบไม่เกิน 2,500" แล้วค้นสินค้าจริงจาก Store API

- เรียก LLM ผ่าน backend เท่านั้น key อยู่ใน .env จำกัดจำนวนคำขอต่อผู้ใช้
- ผู้ให้บริการ LLM: [ระบุ]

5.2 ค้นหาด้วยรูปภาพ
- ลูกค้าถ่ายหรืออัปโหลดรูป แล้วได้สินค้าที่คล้ายกัน เสนอวิธีทำ 2 แบบพร้อมค่าใช้จ่ายก่อนลงมือ

5.3 เข้าสู่ระบบด้วย LINE และแจ้งเตือนออเดอร์ทาง LINE

5.4 Push notification ของ PWA และสินค้าแนะนำเฉพาะคนในหน้าแรก

เสร็จเมื่อ: ฟีเจอร์ทำงานกับข้อมูลจริง มี test และปิดฟีเจอร์ได้ด้วยตัวแปรใน .env
```

## ระยะ 6: ขึ้น production

```
เป้าหมาย: ระบบพร้อมเปิดให้ผู้ขายและลูกค้าจริงใช้

งาน (ให้เขียนคำสั่งและ checklist ให้ผมรันบน VPS เอง ห้ามเชื่อมต่อ VPS เองโดยไม่ถาม)
1. ตรวจ infra/docker-compose.yml สำหรับ production: restart policy, healthcheck, จำกัดหน่วยความจำ, ไม่เปิดพอร์ตฐานข้อมูลออกภายนอก
2. สคริปต์สำรองฐานข้อมูลรายวัน เก็บนอกเครื่อง และขั้นตอนกู้คืนที่ทดลองแล้ว
3. GitHub Actions: build, test, แล้ว deploy เมื่อ merge เข้า main
4. ตรวจความปลอดภัย: rate limit, security headers, สิทธิ์ของ vendor (ผู้ขายเห็นเฉพาะข้อมูลร้านตัวเอง), ตรวจ dependency ที่มีช่องโหว่
5. หน้าเนื้อหา: ข้อตกลงการใช้งาน, ข้อตกลงผู้ขาย, นโยบายความเป็นส่วนตัว (PDPA), แบนเนอร์ขอความยินยอม cookie ใส่เป็นโครงร่างและระบุชัดว่าต้องให้นักกฎหมายตรวจ
6. ทดสอบ end-to-end ด้วย Playwright: สมัคร, ค้นหา, สั่งซื้อ, ผู้ขายจัดส่ง
7. docs/RUNBOOK.md: วิธี deploy, rollback, ดู log, กู้ข้อมูล

เสร็จเมื่อ
- ทั้ง 3 โดเมนเปิดผ่าน HTTPS
- test end-to-end ผ่านบน production ด้วย key ทดสอบ ก่อนสลับเป็น key จริง
- กู้ฐานข้อมูลจากไฟล์สำรองได้จริง
```
